Эта глава написана как сборка, а не как описание. Начинаем с самой дешёвой оценки того, где машина, узнаём, чего она не может, добавляем один датчик и повторяем. Читайте эту главу про оценщик, а не про руление

Ничто в тракте управления не подписано на localization/pose. Единственный подписчик — отладочный выход, а поперечный контроллер берёт скорость рыска прямо из vehicle/chassis. Это делает данное место самым безопасным в проекте для изучения оценщика: можно ошибиться грубо, и машина не заметит. Это же означает, что каждое утверждение ниже пришлось проверять против GNSS, а не против «машина поехала нормально».

Опорные точки в коде, в порядке, в котором глава до них доходит:

  • SpeedFilter (utils/speed_filter.h) — скорости колёс → скорость и ускорение

  • ImuCalibrator / ImuCalibService — IMU телефона → скорость рыска машины

  • GpsLocalProjector — широта и долгота → метры на восток и север

  • VehicleEKF / OnlineLocalizer / LocalizationService — слияние → localization/pose

RPY камеры для warp Supercombo — другая история (калибровка); с IMU у неё общий только prior крепления, и она опционально подаёт в EKF скорость рыска от камерной одометрии.

Шаг 1: самая дешёвая оценка — скорость колёс и угол руля#

Скорость выглядит скучным входом. Это не так, по двум причинам: ею масштабируется весь поперечный тракт (недокрут входит как \(v^2\)), и очевидный способ посчитать по ней ускорение неверен.

Откуда она берётся#

ESP_02 несёт четыре скорости колёс. Декодер их усредняет. Upstream затем гоняет по этому среднему фильтр Калмана из двух состояний (скорость, ускорение) — CarInterfaceBase.update_speed_kf в flowpilot — и берёт из фильтра и vEgo, и aEgo. Мы делаем то же с одним отличием: их коэффициенты запечены под такт 100 Гц, а наши считаются из фактического интервала между кадрами, потому что ESP_02 приходит не по метроному.

Почему нельзя просто продифференцировать#

Потому что сигнал скорости колеса квантован с шагом 0.0075 км/ч, а интервал около 10 мс. Дифференцирование квантованного сигнала на коротком интервале усиливает квант в \(1/dt\) раз. Измерено на настоящем 28-минутном заезде, наивная конечная разность дала:

Машина не может изменить ускорение на 4 м/с² за 10 мс. Это поле было шумом квантования под именем ускорения. Никто его не читал — только поэтому вреда и не было, — а урок в том, что неиспользуемый сигнал не является безвредным: это ловушка, поставленная для того, кто воспользуется им следующим.

Отфильтрованная скорость отличается от сырого среднего на 0.010 м/с медианно, то есть ничего не искажено; ушёл только шум, который дифференцировали.

import math
import numpy as np

QUANTUM = 0.0075 / 3.6      # ESP_VL_Radgeschw_02 resolution, m/s

class SpeedFilter:
    """Two-state (speed, accel) Kalman over the wheel-speed average. Mirror of speed_filter.h."""

    def __init__(self, accel_process_noise=1.5, speed_noise=0.05, jump=2.0, factor=1.0):
        self.qa, self.r, self.jump, self.factor = accel_process_noise, speed_noise**2, jump, factor
        self.inited = False

    def update(self, v_raw, dt):
        z = v_raw * self.factor
        if not self.inited or not dt > 0 or dt > 0.5 or abs(z - self.v) > self.jump:
            self.v, self.a = z, 0.0
            self.pvv, self.pva, self.paa = self.r, 0.0, 1.0
            self.inited = True
            return
        self.v += self.a * dt                                   # predict
        q = self.qa**2 * dt
        pvv = self.pvv + 2 * dt * self.pva + dt**2 * self.paa + q * dt**2 / 3
        pva = self.pva + dt * self.paa + q * dt / 2
        self.pvv, self.pva, self.paa = pvv, pva, self.paa + q
        s = self.pvv + self.r                                   # update on speed only
        kv, ka = self.pvv / s, self.pva / s
        innov = z - self.v
        self.v += kv * innov
        self.a += ka * innov
        self.pvv, self.pva, self.paa = (1 - kv) * self.pvv, (1 - kv) * self.pva, self.paa - ka * self.pva


def quantise(v):
    return round(v / QUANTUM) * QUANTUM

# Steady 20 m/s with a little road noise: what does each method call "acceleration"?
rng = np.random.default_rng(0)
f = SpeedFilter()
naive, filtered, prev = [], [], None
for _ in range(3000):
    z = quantise(20.0 + rng.normal(0, 0.02))
    if prev is not None:
        naive.append((z - prev) / 0.01)
    prev = z
    f.update(z, 0.01)
    filtered.append(f.a)

print(f"naive    : |a| up to {max(abs(x) for x in naive):7.1f} m/s^2")
print(f"filtered : |a| up to {max(abs(x) for x in filtered[500:]):7.2f} m/s^2")

SpeedFilter::Config::wheel_speed_factor для этого и существует, по умолчанию 1.0, чтобы поправка приходила осознанным изменением.

Ошибка скорости в 1.2 % — не задача на 1.2 %

Компенсация недокрута — это \(\kappa = \delta / (L(1 + K v^2))\), скорость входит квадратом. И метрический масштаб модели, который в этом проекте фигурирует как 0.888, измерялся против скорости колёс; против истины он 0.899. Когда сам эталон смещён, каждое производное число это наследует.

Шаг 2a: сделать гироскоп телефона пригодным#

Телефон зажат под тем углом, какой позволяет крепление. Сырой гироскоп — в осях телефона; велосипедной модели нужна скорость рыска машины \(\dot\psi\).

Процедура захвата (ImuCalibrator)#

  1. Нужна скорость с шасси. Стоим: \(v < 0.5\) км/ч.

  2. Тихо: \(\big|\|a\| - g\big| \le 1.5\) м/с² и \(\|\omega\| \le 0.08\) рад/с.

  3. Собрать ≥ 50 отсчётов акселерометра и гироскопа →

    • ориентация \(R\): повернуть измеренную гравитацию на вниз машины \((-Z)\);

    • смещение \(b\): среднее гироскопа.

  4. Пока по-прежнему тихо: экспоненциальное сглаживание смещения с \(\alpha = 0.02\).

  5. Выход (на Android по умолчанию invert_yaw_rate=true):

\[ \dot\psi = \pm \big(R(\omega - b)\big)_z. \]

Отметьте, что эта процедура может дать, а что нет. Гравитация фиксирует два угла из трёх — крен и тангаж телефона относительно машины. Рыск по гравитации не наблюдаем вообще, поэтому и существует prior крепления, и поэтому камера с IMU его делят.

Prior крепления#

Если calibration.camera.rpy_deg задан, те же крен, тангаж и рыск засевают

\[ R = R_z(\mathrm{yaw})\,R_y(\mathrm{pitch})\,R_x(\mathrm{roll}) \]

и сервис может публиковать скорость рыска до захвата на месте (ready = has_prior ∨ orientation_locked).

import numpy as np

g = 9.81

def rotation_from_gravity(accel):
    """Rotate the measured gravity direction onto vehicle +down (-Z), Rodrigues from two vectors."""
    a = np.asarray(accel, dtype=float)
    a = a / np.linalg.norm(a)
    target = np.array([0.0, 0.0, -1.0])
    v = np.cross(a, target)
    c = float(np.dot(a, target))
    if np.linalg.norm(v) < 1e-9:
        return np.eye(3) if c > 0 else np.diag([1.0, -1.0, -1.0])
    vx = np.array([[0, -v[2], v[1]], [v[2], 0, -v[0]], [-v[1], v[0], 0]])
    return np.eye(3) + vx + vx @ vx * (1.0 / (1.0 + c))

def yaw_rate_from_gyro(gyro, R, bias, invert=True):
    w = R @ (np.asarray(gyro) - np.asarray(bias))
    return float(-w[2] if invert else w[2])

R = rotation_from_gravity([0.2, 0.0, -g])       # nearly upright, slight pitch
bias = np.array([0.01, -0.02, 0.005])
gyro = bias + np.array([0.0, 0.0, 0.12])
print("R =\n", np.round(R, 3))
print("yaw_rate =", round(yaw_rate_from_gyro(gyro, R, bias), 4), "rad/s")

Подсказка перед выездом

Постойте несколько секунд после запуска двигателя, чтобы ориентация захватилась. Плохой prior плюс отсутствие захвата дают неверный знак или огромное смещение, и тогда гейт согласия в EKF отбрасывает IMU целиком (\(|\omega - v\tan\delta/L| < 0.35\) рад/с) — фильтр замолкает именно тогда, когда он был нужен.

Шаг 2b: слияние с гироскопом и ошибка, которую стоит изучить#

Состояние \([x,\ y,\ \psi,\ v,\ \dot\psi]^\top\) в ENU. Тик по шасси, примерно каждые 10 мс.

Предсказание#

\[\begin{split} \begin{aligned} x &\leftarrow x + v\cos\psi\,dt,\\ y &\leftarrow y + v\sin\psi\,dt,\\ \psi &\leftarrow \psi + \dot\psi\,dt,\\ v &\leftarrow v_{\text{measured}}. \end{aligned} \end{split}\]

Интересный вопрос: какая \(\dot\psi\)?

Что фильтр делал раньше и почему это было неверно#

Исходный код двигал курс велосипедной моделью, \(\dot\psi_{\text{pred}} = v\tan\delta/L\), и затем перезатирал состояние скорости рыска этим же значением. Каждый шаг. То есть всё, чему научил фильтр гироскоп, выбрасывалось до прихода следующего измерения, а само измерение могло дойти до курса только через взаимную ковариацию \(P_{\psi\dot\psi}\) за один шаг.

Сколько это — «только через взаимную ковариацию»? Легко угадать \(dt\) и ошибиться; я так и сделал. Разберём: обновление скорости рыска имеет усиление \(K_4 = P_{44}/(P_{44}+R)\), а курс получает \(K_2 = P_{24}/(P_{44}+R)\). При \(F_{24} = dt\) предсказанный перекрёстный член равен \(P_{24} \approx dt\,P_{44}\), поэтому

\[ K_2 \approx dt\,\frac{P_{44}}{P_{44}+R} = dt\,K_4 . \]

Это неверный ответ, и причина в том, что сама \(P_{44}\) сжата предыдущим обновлением. Прогоните рекурсию численно с настоящими \(Q_{44} = 0.05^2\) и \(R_{\text{imu}} = 0.02^2\), и установившийся вес окажется \(dt\,(1-K_4) \approx 0.12\,dt\) — то есть курс выходил как

\[ \psi \approx 0.88 \cdot (\text{велосипедная модель}) + 0.12 \cdot (\text{измерение}). \]

Смоделируйте, прежде чем утверждать. Аналитическая прикидка и рекурсия расходятся в семь раз.

Такое разделение было бы нормально, будь велосипедная модель верна. На этой машине она неверна: измеренная передача недокрута \(\kappa_{\text{fact}}/\kappa_{\text{kin}} = 0.54\) при 22 м/с, значит кинематическое предсказание перекручивает в \(1/0.54 = 1.85\) раза, и курс вращался примерно в 1.75 раза быстрее правды. На 30-секундной дуге при 0.15 рад/с это 450° вместо 258°.

Почему ни один заезд этого не показал? Потому что updateGpsYaw жёстко защёлкивает курс всякий раз, когда курс GPS расходится больше чем на 0.5 рад. Фильтр несколько раз в минуту затягивало обратно в строй, и логи выглядели здоровыми. Дефект, замаскированный коррекцией, остаётся дефектом — он всплывает в момент, когда коррекция недоступна, а для GPS это тоннели, городские каньоны и холодный старт.

Что он делает теперь#

Скорость рыска — состояние со своим случайным блужданием, курс интегрирует состояние, а велосипедная модель входит слабым измерением с \(R_{\text{model}} = 0.15^2\) против \(0.02^2\) у гироскопа. Слабым потому, что 0.15 рад/с — это примерно то, насколько они расходятся при 20 м/с и 10° руля. Итого:

  • гироскопу доверяют, и его коррекция доживает до следующего шага;

  • модель всё равно затыкает дыры — если IMU станет невалидным, а CAN продолжит сообщать угол руля, курс продолжит двигаться, а не замрёт;

  • обновления от модели считаются отдельно (model_update_count), поэтому диагностика по-прежнему говорит, каким датчиком получен курс.

setYawRateIsAState(false) в точности возвращает старое поведение — именно так эти два и сравнивали.

Воспроизвести оба, в двадцати строках#

Это вся глава в одном запускаемом блоке: катим установившуюся дугу, где гироскоп говорит правду, а угол руля заявляет в 1.85 раза больше, и смотрим на курс.

import math
import numpy as np

L, DT = 2.636, 0.01
UNDERSTEER = 0.54          # measured kappa_fact / kappa_kin at 22 m/s

class Ekf:
    """[x, y, yaw, v, yaw_rate] in ENU. yaw_rate_is_state=False is the old behaviour."""

    def __init__(self, yaw_rate_is_state=True, r_model=0.15**2, r_imu=0.02**2):
        self.x = np.zeros(5)
        self.P = np.diag([1.0, 1.0, 0.05**2, 0.5**2, 0.05**2])
        self.Q = np.diag([0.1**2, 0.1**2, 0.01**2, 0.5**2, 0.05**2])
        self.as_state, self.r_model, self.r_imu = yaw_rate_is_state, r_model, r_imu

    def predict(self, v_meas, steer, dt):
        x, y, yaw, v = self.x[0], self.x[1], self.x[2], self.x[3]
        model_rate = v_meas * math.tan(steer) / L if abs(steer) > 1e-3 and abs(v_meas) > 0.01 else 0.0
        rate = self.x[4] if self.as_state else model_rate

        self.x[0] = x + v * math.cos(yaw) * dt
        self.x[1] = y + v * math.sin(yaw) * dt
        self.x[2] = yaw + rate * dt
        self.x[3] = v_meas
        if not self.as_state:
            self.x[4] = model_rate                       # <-- the mistake

        F = np.eye(5)
        F[0, 2], F[0, 3] = -v * math.sin(yaw) * dt, math.cos(yaw) * dt
        F[1, 2], F[1, 3] = v * math.cos(yaw) * dt, math.sin(yaw) * dt
        F[2, 4] = dt
        self.P = F @ self.P @ F.T + self.Q

        if self.as_state and model_rate != 0.0:
            self.observe_yaw_rate(model_rate, self.r_model)   # model as a weak measurement

    def observe_yaw_rate(self, z, r):
        H = np.zeros((1, 5))
        H[0, 4] = 1.0
        S = float((H @ self.P @ H.T).item()) + r
        K = (self.P @ H.T / S).ravel()
        self.x = self.x + K * (z - self.x[4])
        IKH = np.eye(5) - np.outer(K, H)
        self.P = IKH @ self.P @ IKH.T + r * np.outer(K, K)

    def observe_gyro(self, z):
        self.observe_yaw_rate(z, self.r_imu)


def drive_arc(as_state, seconds=5.0, v=22.0, steer=0.04, feed_gyro=True):
    ekf = Ekf(yaw_rate_is_state=as_state)
    ekf.x[3] = v
    model_rate = v * math.tan(steer) / L
    truth_rate = UNDERSTEER * model_rate
    for _ in range(int(seconds / DT)):
        ekf.predict(v, steer, DT)
        if feed_gyro:
            ekf.observe_gyro(truth_rate)
    return math.degrees(ekf.x[2]), math.degrees(truth_rate * seconds), math.degrees(model_rate * seconds)

before, _, _ = drive_arc(as_state=False)
print(f"truth heading after 5 s : {truth:6.2f}°   (gyro, the only honest witness)")
print(f"bicycle model would say : {model:6.2f}°   (over-turns by 1/0.54)")
print(f"yaw rate as a state     : {now:6.2f}°   <- tracks the gyro")
print(f"old, overwritten        : {before:6.2f}°   <- tracks the model")

# And the gyro-less case: the model must still drive heading, not freeze it.
no_gyro, _, model5 = drive_arc(as_state=True, feed_gyro=False)

Шаг 3a: GPS → локальные метры#

Начало \((\phi_0,\lambda_0)\) — первый валидный фикс. С радиусом Земли \(R = 6\,371\,000\) м:

\[\begin{split} \begin{aligned} \Delta\phi &= (\phi-\phi_0)\tfrac{\pi}{180},& \Delta\lambda &= (\lambda-\lambda_0)\tfrac{\pi}{180},\\ y &= R\,\Delta\phi && \text{(север)},\\ x &= R\,\Delta\lambda\cos\phi_0 && \text{(восток)}. \end{aligned} \end{split}\]

Пеленг (градусы от севера по часовой) → рыск в ENU (от востока против часовой):

\[ \psi = \mathrm{normalize}\Big(\tfrac{\pi}{2} - b_{\deg}\tfrac{\pi}{180}\Big). \]

Это \(\tfrac{\pi}{2} - b\) стоит выжечь в памяти. Однажды перевёрнутое, оно дало в анализе заезда сообщение об ошибке курса в 103° там, где настоящая ошибка была 0.3°, и час ушёл на охоту за несуществующей ошибкой фильтра.

Курсу доверяют только выше \(v > 2\) м/с, а особенность стояния (\(v < 0.5\) при почти нулевом пеленге) отбрасывается. Затем \(v_x = v\sin b\), \(v_y = v\cos b\).

import math

R_EARTH = 6_371_000.0

def enu_from_ll(lat_deg, lon_deg, lat0_deg, lon0_deg):
    dlat = math.radians(lat_deg - lat0_deg)
    dlon = math.radians(lon_deg - lon0_deg)
    y = dlat * R_EARTH                                       # North
    x = dlon * math.cos(math.radians(lat0_deg)) * R_EARTH     # East
    return x, y

def yaw_enu_from_bearing_deg(bearing_deg):
    return (math.pi / 2 - math.radians(bearing_deg) + math.pi) % (2 * math.pi) - math.pi

print(enu_from_ll(55.001, 37.001, 55.0, 37.0))   # ~(64 m East, 111 m North) at φ₀=55°
for b in (0.0, 90.0, 180.0, 270.0):
    print(f"bearing {b:5.0f}° → ENU yaw {math.degrees(yaw_enu_from_bearing_deg(b)):+7.1f}°")

Шаг 4: как сделать, чтобы коррекция дожила, и обнаружить, что этого всё равно мало#

Шаг 3 дал ограниченные позицию и курс. Он не дал заслуживающей доверия скорости, и причина той же формы, что в шаге 2, — это стоит увидеть дважды, потому что так фильтр Калмана тихо выводят из строя чаще всего.

updateGpsVel вызывался. Но predict делал state_(3) = v_measured на каждом тике, то есть примерно каждые 10 мс, а скорость GPS приходит раз в 0.2 с. Значит коррекцию перезаписывало около двадцати раз до прихода следующей. Слитая скорость была скоростью колёс с точностью до шестого знака.

Была и вторая, независимая причина: обновлению задали R = 1.0, то есть предположенный шум доплера в 1 м/с. Измеренный доплер на порядок лучше — остаток против скорости колёс с исправленным масштабом составляет 0.066–0.101 м/с, и в него входят оба датчика плюс дискретизация 1 Гц.

Две причины взаимодействуют так, что стоит предсказать до запуска кода. В старом режиме с присваиванием дисперсию скорости ничто не сжимало, поэтому она росла без границы и усиление GPS подходило к единице: обновление сдвигало скорость полностью к значению GPS, а следующий тик это выбрасывал. Сделайте скорость состоянием — и дисперсия теперь мала, поэтому при R = 1.0 обновление почти не регистрируется. Только с обеими правками оно и попадает, и держится.

Обе исправлены: скорость — состояние (setSpeedIsAState), а gps_vel_R равно \(0.1^2\).

# The two failure modes and the fix, in one experiment. True speed 20.0; CAN reports 20.24 (the measured
# 1.2 % scale); GPS velocity reports the truth once every 20 ticks.
class SpeedState:
    """The speed part of the EKF, with the old behaviour available for comparison."""

    def __init__(self, as_state=True, q=0.5**2, r_wheel=0.1**2):
        self.as_state, self.q, self.r_wheel = as_state, q, r_wheel
        self.v, self.p = 20.0, 1.0

    def predict(self, v_wheel):
        if not self.as_state:
            self.v = v_wheel                      # <-- the assignment that erased everything
            self.p += self.q
            return
        self.p += self.q
        k = self.p / (self.p + self.r_wheel)       # wheel speed as a measurement
        self.v += k * (v_wheel - self.v)
        self.p *= 1 - k

    def observe_gps(self, v_gps, r_gps):
        k = self.p / (self.p + r_gps)
        self.v += k * (v_gps - self.v)
        self.p *= 1 - k


def run(as_state, r_gps, ticks=400, every=20):
    f = SpeedState(as_state=as_state)
    right_after = None
    for i in range(ticks):
        f.predict(20.24)
        if i % every == 0:
            f.observe_gps(20.0, r_gps)
            right_after = f.v
    return right_after, f.v

for label, as_state, r_gps in (("assigned, R=1.0  (as shipped before)", False, 1.0),
                               ("state,    R=1.0  (noise still assumed)", True, 1.0),
                               ("state,    R=0.01 (Doppler as measured)", True, 0.1**2)):
    after, end = run(as_state, r_gps)
    print(f"{label}: right after GPS {after:.4f}, one GPS period later {end:.4f}")

Это не провал настройки, а неидентифицируемость. Смещённое измерение приходит в двадцать раз чаще при том же предполагаемом шуме, поэтому между посылками выигрывает оно; и никакая пара предположений о несмещённом шуме не отделит постоянное смещение на частом измерении от истины. Понизить доверие к колёсам значило бы выбросить их по-настоящему низкий шум и ухудшить оценку везде.

Выход — перестать делать вид, что смещение это шум, и дать ему собственное состояние: оценивать масштаб. Именно это paramsd делает для параметров машины, и поэтому шаг 5 — то место, где эта глава останавливается, а та работа начинается.

Шаг 5: чего до сих пор нет#

  • Крен дороги теперь есть, уклона нет. RoadRollEstimator читает его из поперечного акселерометра — sin(φ) = (a_y − f_y)/g при a_y = −v·yaw_rate, — вычитает измеренные +3 °/g крена кузова на подвеске и публикует на localization/pose вместе со своей неопределённостью: 2.2° на отсчёт, 0.65° после десяти секунд усреднения и не лучше, потому что остаток — это смена уклона дороги вдоль маршрута. Гейт ставьте на road_roll_std_deg, который начинается с тех же 10°, что paramsd использует для «крена нет». Продольный уклон — та же конструкция с f_x, и он не сделан.

    Две вещи, которые стоили времени и стоят того, чтобы их унести: знак chassis.yaw_rate — ISO, с z вверх и плюсом влево, тогда как фрейм оценщика с z вниз, и перевёрнутый знак сообщает не ошибку, а градиент крена кузова 116 °/g; и захват ориентации на месте раньше перезаписывал курс крепления вращением из гравитации, что безвредно для скорости рыска и убивает всё поперечное.

  • Масштаб скорости колёс всё ещё вводится руками. Скорость GPS используется, скорость стала состоянием, и этого не хватило (шаг 4): частое смещённое измерение выигрывает между посылками GPS, и никакое предположение о шуме не отделяет постоянное смещение от истины. Масштабу нужно собственное состояние.

  • Выученные параметры машины — сделаны, и результат это шаг 6 ниже. В списке пробелов их больше нет: порт есть, он измерен, и измерение и есть причина, по которой он отгружается выключенным.

Порядок зависимостей стоит проговорить, потому что его легко перевернуть: скорость GPS в фильтр → оценка ориентации и крена → paramsd. Портировать paramsd первым значит оставить его вход по крену прижатым к нулю; это работает, но отдаёт единственное, что отличает поперечный уклон дороги от недокрута машины. Этот порядок был соблюдён, и шаг 6 — это то, что вышло, когда вход по крену, которого он требовал, встретился с бюджетом ошибок, в который обязан был поместиться.

Шаг 6: учим параметры машины — и что об этом сказало измерение#

Всё до сих пор оценивало, где машина. Этот шаг оценивает, какая она — и он в этой главе, а не в главе про поперечное управление, потому что входы оценщика — это входы локализатора, а его единственный неочевидный вход есть крен дороги из шага 5.

Чем быстрее, тем устойчивее машина поворачивает меньше, чем предсказывает кинематика. tire_stiffness_factor — одно число в файле конфига. Одно число не может быть и 0.89, и 0.46. Значит, говорит рассуждение, оно должно стать состоянием — что и делает paramsd у upstream.

Верно всё, кроме слова «значит». Скоростную зависимость несёт не константа, а модель вокруг неё. Вспомним из главы про поперечное управление:

\[\kappa = \frac{\tan\delta}{L\,(1 - \text{slip}\cdot v^2)}\]

где \(\text{slip} < 0\) для недокручивающей машины, поэтому знаменатель растёт как \(v^2\) и тот же угол руля покупает меньше кривизны на скорости. Это ровно наблюдаемый эффект. Значит, вопрос не «падает ли отношение со скоростью» — падает, — а «падает ли оно по-прежнему после того, как модель сказала своё слово».

import numpy as np

WHEELBASE_M = 2.636
C2F_FRAC = 0.45
MASS_KG = 1533.0


def slip_factor(tsf: float) -> float:
    """Transcribed from utils/vehicle_model.h. Negative for an understeering car."""
    civic_mass, civic_wb = 1326.0 + 136.0, 2.70
    civic_c2f = civic_wb * 0.4
    a_f = WHEELBASE_M * C2F_FRAC
    a_r = WHEELBASE_M - a_f
    c_f = 192150.0 * tsf * MASS_KG / civic_mass * (a_r / WHEELBASE_M) / ((civic_wb - civic_c2f) / civic_wb)
    c_r = 202500.0 * tsf * MASS_KG / civic_mass * (a_f / WHEELBASE_M) / (civic_c2f / civic_wb)
    return MASS_KG * (C2F_FRAC * c_f - (1.0 - C2F_FRAC) * c_r) / (WHEELBASE_M * c_f * c_r)

(Этот прогон берёт середину каждой полосы; посчитанные по отсчётам прямо из бага остаточные отношения дают 0.95, 0.94, 0.99, 0.87, 0.89, 0.80 — картина та же.) Ровная недостача около 10 % — это не скоростная зависимость жёсткости. Это ошибка масштаба, а ошибка масштаба есть одно число, то есть ровно то, чем константа быть умеет.

Порт это не остановило — фильтр, сообщающий свою неопределённость, всё равно стоит иметь, и те 10 % всё равно требуют объяснения. Но это меняет то, как выглядел бы успех.

Оценщик#

Три состояния, измерение — скорость рыска:

\[x = [\text{tsf},\ \text{передаточное},\ \text{смещение угла}], \qquad \dot\psi_{\text{пред}} = v\,\kappa(x) + \frac{g\sin\phi}{v}\]

Две детали несут почти всю ценность.

Берите собственную функцию кривизны контроллера. Не её пересказ, а ту же самую функцию. Параметр, выученный против модели, чуть отличающейся от той, которая его потребляет, хуже настроенной руками константы, потому что выглядит принципиальным.

Дифференцируйте её численно. Три состояния на частоте CAN не стоят ничего, а аналитическая производная через slip_factor — которая делит на произведения жёсткостей, сами зависящие от состояния, — это ровно то выражение, которое месяц бывает неверным, прежде чем кто-нибудь заметит. Функция измерения есть единственный источник истины; центральная разность не может с ней разойтись.

G = 9.81
STEER_SIGN = -1.0     # positive CAN angle is a LEFT turn on this car; this frame is z-down


def predict_yaw(x, v, swa_deg, roll_deg):
    """Yaw rate in the z-down frame. The controller's own model, evaluated at the state x."""
    tsf, ratio, offset = x
    v = max(v, 1e-3)
    delta = STEER_SIGN * np.radians(swa_deg - offset) / max(ratio, 1e-3)
    kappa = np.tan(delta) / (WHEELBASE_M * (1.0 - slip_factor(max(tsf, 1e-3)) * v * v))
    return v * kappa + G * np.sin(np.radians(roll_deg)) / v


class ParamsLearner:
    def __init__(self, ratio_std=0.1, use_roll=False):
        self.x = np.array([0.64, 15.7, 0.0])
        self.p = np.array([0.5 ** 2, ratio_std ** 2, 1.0 ** 2])
        self.q = np.array([0.005 ** 2, 0.00005 ** 2, 0.02 ** 2])
        self.p_max = np.array([0.5 ** 2, max(ratio_std, 0.3) ** 2, np.inf])
        self.lo = np.array([0.2, 12.0, -10.0])
        self.hi = np.array([5.0, 20.0, 10.0])
        self.r = 0.02 ** 2
        self.use_roll = use_roll
        self.n = 0

    def update(self, v, swa_deg, yaw_rate_can, roll_deg, dt):
        if v < 5.0 or abs(swa_deg) > 45.0:
            return
        yaw = -yaw_rate_can                       # ISO in (left-positive), z-down inside
        roll = roll_deg if self.use_roll else 0.0
        self.p = self.p + self.q * dt

        h = np.zeros(3)
        eps = np.array([1e-4, 1e-3, 1e-3])
        for i in range(3):
            xp, xm = self.x.copy(), self.x.copy()
            xp[i] += eps[i]
            xm[i] -= eps[i]
            h[i] = (predict_yaw(xp, v, swa_deg, roll) - predict_yaw(xm, v, swa_deg, roll)) / (2 * eps[i])

        k = (self.p * h) / (float(h @ (self.p * h)) + self.r)
        self.x = np.clip(self.x + k * (yaw - predict_yaw(self.x, v, swa_deg, roll)), self.lo, self.hi)
        self.p = self.p * (1.0 - k * h)
        self.p = np.minimum(self.p, self.p_max)   # a ceiling, not a pseudo-measurement — see below
        self.n += 1

    def valid(self):
        """Count, sigma, AND bounds. Each catches what the others miss."""
        return (self.n >= 500 and np.sqrt(self.p[0]) < 0.15
                and bool(np.all(self.x > self.lo + 1e-9)) and bool(np.all(self.x < self.hi - 1e-9)))

Ловушка, которую вам ставит код upstream#

paramsd не даёт неопределённости медленных параметров расти на длинных прямых и записывает это как наблюдать состояние его же текущим значением при большом шуме. Скопируйте буквально — получите баг. Невязка \(z - x\) тождественно нулевая, поэтому обновление не может сдвинуть оценку, оно может только сжать ковариацию. Применённое раз на сообщение локализатора это безвредная граница. Применённое на каждом отсчёте CAN на 100 Гц оно жмёт ковариацию сто раз в секунду, пока не приходит ни бита информации, настоящее измерение теряет весь вес, и фильтр замерзает возле того, откуда начал. Измерено на синтетическом тесте восстановления: истинная жёсткость 0.45 вышла как 0.515, прижатая к 0.64, с которых он стартовал, — а valid() прочёл сжатую сигму как сходимость после десяти минут прямой дороги.

Поэтому это потолок: сигма не может превысить границу, а уменьшать её вправе только настоящие измерения. Это и есть строчка np.minimum выше.

Два отказа, которые синтетика найти не могла#

Оба нашлись при прогоне отгружаемого фильтра по записанному заезду — это и есть аргумент за то, чтобы строить офлайн-реплей одновременно с фильтром.

Знак руля. Порт менял знак рыска на входе — ISO в z-вниз, верно — и не применял vehicle.steer_sign этой машины, который контроллер применял всегда. На этой машине положительный угол на CAN есть поворот влево: регрессия измеренного ISO-рыска на кинематическое предсказание даёт наклон \(+0.824\) при корреляции \(0.987\) на 28 636 отсчётах в дугах. То есть предсказание противостояло измерению в каждом повороте.

И valid() всё равно сказал «да». Фильтр ушёл в те границы, которые уменьшают предсказанную величину: жёсткость на пол 0.200, передаточное на потолок 20.0, одинаково во всех четырёх четвертях заезда. Насыщенное состояние перестало двигаться, значит его сигма мала, значит выглядит оно в точности как сходимость. Тогдашний valid() проверял границы жёсткости и не проверял границы передаточного — и пропустил.

def drive(learner, corners, truth_tsf=0.64, truth_ratio=15.7, sign=STEER_SIGN):
    """Feed steady corners generated by a known car, in the ISO convention the CAN decoder produces."""
    for swa, v in corners:
        delta = sign * np.radians(swa) / truth_ratio
        kappa = np.tan(delta) / (WHEELBASE_M * (1.0 - slip_factor(truth_tsf) * v * v))
        yaw_iso = -v * kappa                      # z-down truth back to ISO, as ESP_02 reports it
        for _ in range(60):
            learner.update(v, swa, yaw_iso, 0.0, 0.01)


corners = [(swa, v) for _ in range(12)

Заметьте, что valid() выше сообщает False для прогона с перевёрнутым знаком — это исправленная проверка, та, что сверяет с границами каждое состояние. Тогдашняя проверяла только счётчик и сигму, и третий print объясняет, почему это проходило: сигма насыщенной жёсткости равна 0.010, спокойно под порогом 0.15, потому что у состояния, которое перестало двигаться, ковариация мала.

Так что границы — не подстраховка ради аккуратности. Они единственное, что отличает насыщенную оценку от сошедшейся, и проверка валидности, пропускающая границы хоть одного состояния, имеет дыру ровно там, где живёт худший отказ.

Почему крен дороги в итоге не используется#

Шаг 5 строил оценку крена именно потому, что поперечный уклон дороги и недокрут машины дают одинаковую подпись поперечного ускорения, и paramsd без неё их не разделит. Этот аргумент верен. Он же на этом железе не имеет значения — и арифметика, которая это показывает, занимает две строки.

for v in (10.0, 15.0, 25.0):
    print(f"{v:5.1f} m/s: 1 deg of bank = {G * np.sin(np.radians(1.0)) / v:.4f} rad/s of yaw")
print("flat-model yaw residual on the real drive: 0.0065 rad/s")
print("bank estimate accuracy from a windscreen phone, at its floor: 0.65 deg")

Один градус уклона на 15 м/с — это 0.0114 рад/с, почти вдвое больше всего остатка, который у плоской модели уже есть. Наша оценка крена верна до 0.65° после десяти секунд усреднения и не лучше, потому что дальше остаток — это реальная смена поперечного уклона дороги. То есть вход несёт больше ошибки, чем ошибка, которую он был призван убрать. Его подача поднимает остаток с 0.0065 до 0.0104 рад/с, деградация 60 %, и params_use_roll отгружается как false.

С этим стоит посидеть. Аргумент про зависимости — «оценщику нужен крен, значит крен первым» — был верен насчёт интерфейсов и молчал насчёт точности. Достаточно ли \(B\) хорош для \(A\), имеет ответ только после того, как \(B\) существует и измерен против бюджета ошибок \(A\). Здесь бюджет был 0.0065 рад/с, а вход принёс 0.0114.

Поэтому оно отгружается за двумя флагами, и оба выключены#

localization.learn_vehicle_params запускает оценщик. lane_keep.use_learned_params разрешает контроллеру его читать. Раздельно, намеренно: оценщик может публиковать весь заезд, пока контроллер держится констант, — и именно так выученное значение получает право быть использованным. Один флаг на двоих сделал бы первый заезд, проверяющий оценщик, и первым заездом, ему доверяющим.

Даже при обоих включённых контроллер берёт оценку только пока держится learned_params_valid, и откатывается к настроенным константам в тот момент, когда она перестаёт держаться, — то есть потеря валидности возвращает параметры назад, а не замораживает их на том, во что оценщик поверил последним.

Вот и вся функция: собрана, оттестирована, проинструментирована, публикуется, воспроизводится офлайн и выключена. Отрицательный результат, на который можно показать с числами, есть законченная работа.

Как это связано с удержанием полосы#

Поперечным MPC и Pure Pursuit глобальный ENU для руления не нужен — они следят за vision/path в системе device. Локализация важна для:

  • карт по бегам и наложений mapmatch (docs/MAPMATCH.md — это отдельный офлайновый сопоставитель формы трека, и он интегрирует измеренную скорость рыска напрямую, поэтому описанная выше ошибка его никогда не касалась);

  • проверок на разумность — расхождение GPS и чистого счисления пути;

  • любой будущей функции, привязанной к карте;

  • обучение параметров машины, которыми пользуется контроллер, — шаг 6, и единственный потребитель, которому оценка крена в итоге не понадобилась.

Неверный знак IMU не перевернёт руление, пока удержание полосы игнорирует позу, — но отравит каждого потребителя localization/pose и тихо испортит офлайн-разбор.
