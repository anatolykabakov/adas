# Косметический рефакторинг: Java, C++, скрипты — 2026-08-14

Предложения, не меняющие поведение: имена, раскладка файлов, единообразие стиля, повторы. Всё
измерено по дереву, не по памяти. Поведенческие правки и дубли, которые могут разъехаться, — в
[REVIEW_COMPACTION_2026_08_14.md](REVIEW_COMPACTION_2026_08_14.md), здесь они не повторяются.

Объём: Java 29 файлов / 8 390 строк, C++ 135 файлов / 19 690 строк (без вендорного `json11`, `CL/`,
`msm_kgsl`), Python 107 файлов / 26 960 строк.

Порядок: сверху то, что мешает читать каждый день; снизу — вкусовщина, которую можно и не делать.

## C++

### C1. Смесь `.h` и `.hpp` внутри одного каталога

76 заголовков `.h` против 20 `.hpp`, и в трёх каталогах они перемешаны:

| каталог | `.h` | `.hpp` |
|---|---|---|
| `lateral` | 1 | 15 |
| `utils` | 23 | 2 |
| `thneed` | 17 | 1 |

Расширение ничего не значит — но пока их два, каждый новый файл требует решения, а каждый `#include`
— припоминания. Предложение: `.h` везде, кроме `thneed` (вендорное, трогать незачем), то есть
переименовать 15 файлов в `lateral` и 2 в `utils`. Механически, компилятору всё равно.

### C2. `services/` держит только сервисы, но не всё, что снаружи выглядит сервисом

`lane_keep_gates` уже переехал в `utils` — по тому же признаку туда просятся `road_roll_estimator`,
`interval_filter`, `speed_filter`: у них нет ни подписок, ни таймеров, это машинки состояния.
Проверять просто: если класс не наследует `middleware::Service`, ему нечего делать в `services/`.
Сейчас таких нет — правило соблюдено, стоит записать его в `docs/`, чтобы не расползлось.

### C3. Одиннадцать строк длиннее 120 символов

`ColumnLimit: 120` в `.clang-format`, но 11 строк его превышают — это места, где clang-format не может
перенести (длинные строковые литералы в логах). Разбить литералы вручную.

## Java

### J1. Плоский пакет `adas.app` из шестнадцати классов

```
AdasAppHandler  AdasConfig  AudioRecorder  BagLogger  CameraHandler  GPSHandler
IMUHandler  Logger  MainActivity  ParamSlider  PhoneStatsHandler  ProtoUtils
RuntimeParams  TimeUtil  TrafficYoloBenchActivity  ZMQBridgeService
```

Рядом лежат UI (`MainActivity`, `ParamSlider`), драйверы датчиков (`Camera/GPS/IMU/PhoneStats`),
запись (`BagLogger`, `AudioRecorder`), транспорт (`ZMQBridgeService`, `ProtoUtils`) и настройки
(`AdasConfig`, `RuntimeParams`). Подпакет `vision` уже выделен и читается лучше остальных.

Предложение — четыре подпакета по той же логике: `sensors`, `record`, `bridge`, `ui`. Правка чисто
механическая: `package` и `import`, сборка не меняется.

### J2. Шесть методов длиннее 60 строк

| строк | метод |
|---|---|
| 192 | `CameraHandler.startCamera` |
| 191 | `ProtoUtils.createLaneLinesMessage` |
| 181 | `ProtoUtils.getMessageSize` |
| 174 | `TrafficYoloRunner.needsSpeedOcr` |
| 157 | `RuntimeParams.load` |
| 150 | `CameraHandler.logCameraIntrinsics` |

Из них два — таблицы, а не логика: `getMessageSize` и `needsSpeedOcr` перечисляют варианты, их
дробить не надо (как `publishPayload` в мосте). А `startCamera` на 192 строки — это открытие
устройства, конфигурация сессии, поверхности и запуск потока в одном месте; читается тяжело и ровно
там живёт та гонка `CameraDevice was already closed`, которую видно в логе при перезапуске.

### J3. Два `printStackTrace`

Всего два места печатают стек мимо логгера — в проекте есть `Logger`. Заменить, чтобы вывод не
терялся при разборе.

### J4. Двадцать две строки длиннее 120 символов

Java-часть не покрыта форматтером вообще: `.clang-format` есть, `.editorconfig` или
google-java-format — нет. Предложение: добавить конфиг форматтера и прогнать один раз; дальше диффы
перестанут содержать переносы.

## Скрипты (Python)

### S1. Тридцать два скрипта в одном каталоге

Верхний уровень `scripts/` — 32 файла, из них 23 начинаются на `bag_*`. Они уже сгруппированы
префиксом, но не каталогами. Ниже лежат `core/`, `vis/`, `sim/`, `mapmatch/`, `proto/`, `pyadas/` —
то есть структура есть, просто верхний уровень мимо неё.

Предложение: `scripts/bag/` для разборов бегов, `scripts/rlog/` для стендов против чужих логов
(`rlog_lat_diff`, `rlog_arc_offset`), `scripts/tools/` для остального (`panda_flash`,
`camera_calib_chessboard`, `make_chessboard`, `steering_calibration`, `golden`, `latency`). Импорты
не пострадают: они идут через `_path`, а не через относительные пути.

### S2. Шесть файлов правят `sys.path` руками

`_path` импортируется в 44 файлах — это принятый способ. Ещё шесть делают `sys.path.insert` напрямую.
Привести к одному способу.

### S3. Два скрипта без `argparse`

30 из 32 разбирают аргументы через `argparse`, два — вручную. Мелочь, но именно она ломает привычку
«`--help` работает везде».

### S4. Общие помощники расползлись по вызывающим

`bag_io` импортируют 26 файлов, `lane_projection` — 7, `gps_utils` — 4, `osm_layer` — 3,
`bag_cache` — 2. Это здоровая картина. Но рядом живут локальные копии мелочей: `_stat` в
`bag_localization_replay`, `_stat_sort_key` в `export_to_plotjuggler` — форматирование чисел
дублируется в нескольких отчётах. Один `core/report_fmt.py` на медиану/перцентили/строку таблицы
уберёт повтор и сделает отчёты одинаковыми на вид.

### S5. Крупные файлы

| строк | файл |
|---|---|
| 2054 | `vis/interactive_visualizer.py` |
| 953 | `rlog/rlog_lat_diff.py` |
| 928 | `vis/export_to_plotjuggler.py` |
| 917 | `bag/bag_mpc_sim.py` |
| 852 | `core/imu_utils.py` |

`interactive_visualizer` вдвое больше следующего — там UI, загрузка бега, слои и отрисовка в одном
файле. Косметически из него выносятся два независимых куска: описание слоёв (стили, порядок,
видимость) и загрузка данных бега. Остальные четыре — по делу, трогать не стоит.

Проверил отдельно, чтобы не искали: `TODO`/`FIXME`/`HACK` — **ноль** во всём дереве (Java, C++,
Python). `using namespace` в заголовках — ноль. `__pycache__` игнорируется, в индексе нет ни одного
файла. Русских комментариев в C++ не осталось.
