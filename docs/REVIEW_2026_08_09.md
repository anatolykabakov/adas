## 1. Рыскание камеры уходит в EKF с обратным знаком (A)

`LocalizationService::step` берёт из позы модели угловую скорость и отдаёт её в фильтр:

```cpp
if (config_.sources.camera_odometry && have_cam_odo_ && cam_odo_.valid) {
  const double rstd = cam_odo_.rot_std[2];
  if (rstd < 0.5)
    cam_w = cam_odo_.rot[2];
}
loc_.step(dt, msg.speed_mps, msg.steer_rad, yr, gps, std::nullopt, cam_w);
```

`OnlineLocalizer` умеет разворачивать знак — `if (invert_cam_yaw_rate) w = -w;` — но **этот флаг
нигде не читается из конфига**. В `adas_config.cpp` для него нет `setBool`, поэтому он навсегда
`false`. При этом `use_camera_odometry` в поставляемом конфиге стоит `true`.

Измерено на `2026_08_08_23_00_28` (39 188 тиков с позой):

| | |
|---|---|
| корреляция рыскания модели с шиной | **−0.994** |
| проходит ворота EKF | **85.7 %** тиков |
| из них знак противоположен шине | **82.2 %** |
| при рыскании больше 2.9 °/с | 4695 тиков, знак противоположен у **100 %** |

Почему ворота не спасают: проверка `std::abs(w - yr_bicycle) < imu_agree_rad_s` (0.35) сравнивает
величины, а на прямой обе близки к нулю — медиана расхождения на прошедших тиках 0.0134 рад/с. То
есть ворота пропускают именно потому, что рыскания нет, а когда оно появляется, в фильтр уходит
измерение с противоположным знаком.

Вторая половина проблемы: даже с исправленным знаком **масштаб 0.648**, то есть измерение
систематически занижено на треть, и при `|0.65·yr − yr| = 0.35·|yr| < 0.35` оно пролезет в фильтр
почти всегда. Проверено, что это не свойство thneed: у нашей модели через ONNX те же 0.711 / 0.769 /
0.866 на трёх других заездах.

**Исправление.** Отключить источник по умолчанию (`use_camera_odometry: false`) и завести
`invert_cam_yaw_rate` в разбор конфига, чтобы им можно было управлять. Включать обратно — только
после того, как объяснён масштаб: измерение, заниженное на треть, хуже отсутствующего, потому что
фильтр ему верит.

## 2. `prepare_drive.sh` не пересобирает нативную библиотеку (A)

Скрипт называется «подготовить телефон к выезду» и делает `adb install -r "$APK"`, проверив только
дату APK. Но **gradle нативную библиотеку не собирает**: `.so` приходит готовой из
`app/libs/arm64-v8a/` через `app/src/main/cpp/build_cpp.sh`, а `assembleDebug` отрабатывает за три
секунды и упаковывает то, что лежит.

Это не теория. Сегодня при подготовке заезда `assembleDebug` завершился успешно и собрал APK с
библиотекой трёхчасовой давности — **без правки упреждения целиком**. Поймано сверкой времени правок
C++ со временем `.so`; проверять надо было по sha1 библиотеки внутри APK.

Цена ошибки: заезд проводится на старом управлении, а его результат приписывается новому. Это ровно
тот класс ошибок, ради которого ведётся `PREDRIVE.md`.

**Исправление.** Скрипт должен либо звать `build_cpp.sh -t android` и `assembleDebug` сам, либо
отказываться работать, если `.so` внутри APK старше исходников C++.

## 5. Подмена кривизны при точном нуле (B)

```python
out["ctrl_kappa"] = _col(dbg, lambda d: d.mpc_kappa_used or d.pp_curvature)
```

Идиома `a or b` на float подставляет `b`, когда `a == 0.0`, а ноль кривизны — это законное значение
«идеально прямо», а не «данных нет». На проверенном баге оба поля совпадают до знака и случаев
`mpc == 0 при pp != 0` ноль, так что сейчас последствий нет. Но на баге с контроллером `mpc` поля
разойдутся, и разбор молча смешает два источника.

**Исправление.** Выбирать поле по имени контроллера из того же сообщения, а не по истинности числа.

## Пункты 9–18: подробности и что сделано

### 9. Подписка на выученные параметры не срабатывала никогда (A)

`LaneKeepService::configure` подписывался на `localization/pose` **структурой** `LocalizationPose`, а
`LocalizationService::publishPose` публикует на этот топик **сообщение** `ZMQMessage`. Middleware
разбирает подписки по `typeid` и молча роняет несовпадение, а в лог на каждом тике шины (около 100 Гц)
падает `publish type mismatch`.

Следствие: при `lane_keep.use_learned_params = true` обработчик не вызывался, `learned_valid_`
оставался false, и `effectiveStiffnessFactor` / `SteerRatio` / `AngleOffsetDeg` тихо возвращали
константы из конфига. Функция выглядела включённой и не работала. Тесты этого не ловили, потому что
зовут `setLearnedParams` напрямую.

По умолчанию `use_learned_params = false`, поэтому на дороге это ещё не проявлялось.

**Сделано.** Подписка переведена на `ZMQMessage` с разбором `has_localization_pose()`.

### 10 и 11. Поворотник: статус не снимался, таймер не взводился (A)

Две ошибки, вторая пряталась за первой.

`out` — копия `last_`, и `updateTorqueFromAngle` крутится по тикам шины, то есть в несколько раз чаще
кадров зрения. Гейт актюации снимает свой статус симметрично (`no_assist` → `ok`), а ветка поворотника
только повышала `ok` → `blinker`. После возврата в лог писалось «steering again», а статус оставался
`blinker`, `active` — false, команда — ноль, до следующего кадра зрения. Если кадры прекратятся, а шина
идёт — навсегда.

Починив это, получили падение теста. Отладка показала вторую ошибку: признаком «таймер отпускания не
взведён» служил `blinker_off_us_ == 0`, но **ноль — законная метка времени**. В симулированном режиме
`Middleware::now()` возвращает `sim_us_`, который начинается с нуля, поэтому таймер не взводился
никогда и задержка возврата в стенде не проверялась вообще. Тест проходил через застрявший статус.

**Сделано.** Отдельный флаг `blinker_off_armed_` вместо нулевого признака; статус снимается
симметрично; тест переведён на `mw.setTime()` вместо настоящего `sleep_for` — заодно весь стенд стал
втрое быстрее (418 → 162 мс).

### 12. Неизвестная передача открывала актюацию (B)

`gearIsReverse(gear)` возвращает `gear == 6`, а до первого кадра `Getriebe_11` передача читается как 0.
При `lat_always_on: true` предикат `lateralActuationAllowed` полагался только на `cruiseAvailable &&
!gearReverse`, то есть между стартом приложения и первым кадром коробки панде разрешалась поперечная
актюация, хотя машина может стоять на задней.

**Сделано.** В `CarStateView` добавлен `gearKnown`, предикат требует его; декодер выставляет
`gear() != 0`. Тест дополнен случаем неизвестной передачи.

### 13. История кривизн сдвигалась по байтам (B)

```cpp
std::memmove(&prev_curvs_buf[0], &prev_curvs_buf[1], PREV_DESIRED_CURVS_LEN - 1);
```

99 **байт** вместо `sizeof(float) * 99` — сдвигается четверть истории, на границе остаётся
полузаписанный float. Это опечатка flowpilot, перенесённая дословно, и она на нашем пути: буфер
привязан входом модели (`setInputBuffer("prev_desired_curvs", ...)`) и обновляется в нашем
`nativeExecute`.

Раньше я оставил её как есть, рассудив, что менять поведение чужой модели без измерения нечестно. Это
было неверное решение: качество разметки на thneed **не измерено вовсе**, и мусор на входе рекуррентной
модели — первый подозреваемый, а не то, что стоит консервировать.

**Сделано.** Сдвиг по элементам, расхождение с flowpilot помечено в коде.

### 14. Выбор диапазона FPS мог уйти на 60 Гц (B)

Верхняя граница обрезалась целью (`min(r.getUpper(), targetFps)`), а тай-брейк по нижней — нет. На
телефоне, отдающем и `[30,30]`, и `[60,60]`, оба дают верхнюю 30, а по нижней выигрывает `[60,60]` —
и камера уходит на 60 Гц. Это удвоило бы работу потока камеры ради конвейера, который столько не
съест, и вдвое урезало выдержку — ровно та беда со светом, от которой правило и написано.

**Сделано.** Диапазон, чья нижняя граница выше цели, отбрасывается: он целевой темп выдать не может.

### 15. Повторный `nativeInit` оставлял чужое состояние (B)

`nativeInit` возвращает успех, ничего не делая, если модель уже загружена, а `close()` пуст. При
переключении модели на ходу создаётся новый `SupercomboThneedRunner` с `hasPrev = false`, но нативные
`features_buf` (99 кадров фич) и `prev_curvs_buf` хранят прошлую сессию — несогласованное состояние на
первых кадрах после переключения.

**Сделано.** Повторный вызов обнуляет оба буфера.

### 16. `lane_std_range_m` подменялся умолчанием (C)

`const double x_max = range_m > 5.0 ? range_m : 40.0;` — защита от вырожденного окна отображала
**узкие** заданные значения в **самое широкое**. Конфигурация с `lane_std_range_m: 4` получала окно
5–40 м, то есть противоположность заданному, и ничего не писала в лог.

**Сделано.** Зажим снизу `std::max(range_m, 10.0)` вместо подмены.

### 17. Начальный луч против односторонних (C)

Засев начального луча перебирал все `2 * edgeCount()` направленных рёбер и отбрасывал только нулевую
длину, тогда как расширение луча проверяет `oneway`. Маршрут мог начаться с движения против
односторонней: и ширина луча тратится впустую, и наверх выходит вариант, по которому не проехать.

**Сделано.** Та же проверка при засеве.

### 18. `use_cam_odo` мёртв (C)

Комментарий утверждал «зеркалит `sources.camera_odometry`», но после перехода на `sources` поле никем
не читается — только пишется из конфига. Программный вызов, ставящий `use_cam_odo = false`, тихо
оставлял бы камеру включённой.

**Сделано.** Поле и запись в него удалены.
