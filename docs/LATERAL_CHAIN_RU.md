# Поперечный тракт: от линий разметки до момента на руле

Четыре этапа, разбор по механике: что именно происходит с числом на каждом шаге и **почему сделано так**.
Все количественные утверждения здесь — измеренные, с указанием заезда.

Этот документ дополняет [`IMAGE_TO_CAN_PIPELINE.md`](IMAGE_TO_CAN_PIPELINE.md), а не заменяет его. Там —
топология всей цепочки от кадра камеры до CAN, включая зрение, продольный план, UI и сим; здесь — только
поперечное управление и только «как это работает и на чём спотыкается». Если два документа расходятся,
топология правильная там, механика — здесь.

Построчное сравнение с апстримом — `DIFF_FROM_DP_RU.md` (удалён 2026-08-21, история в git): что перенесено дословно, где
разошлись сознательно и что недонесли.

Пределы применимости контроллеров — [`CONTROLLER_LIMITS.md`](CONTROLLER_LIMITS.md), устройство MPC —
`MPC_EXPLAINED.md` (удалён, история в git), диагноз по недоездам команды — §4a и §5a
[`BACKLOG.md`](BACKLOG.md).

## Тракт целиком

| этап | частота | вход → выход | код |
|---|---|---|---|
| 1 | ~14 Гц (кадр) | `LaneLines` → `vision/path` | `utils/lane_path.cpp` |
| 2 | ~14 Гц (кадр) | полилиния → `steer_rad`, `desired_swa_deg` | `services/planner.cpp::onLanes` |

`desired_swa_deg` PID видит примерно **семь раз**.

## Этап 1. Из `vision/lanes` в `vision/path`

`utils/lane_path.cpp`, функция `laneLinesToPath`, вызов из `services/planner.cpp::onLanes`.

Это единственное место, где из выхода нейросети получается опорная траектория. Дальше по тракту никто не
знает про линии разметки — контроллер видит только полилинию.

### Что приходит

Протобуф `LaneLines`: общая сетка `x[]`; четыре полилинии `lanes[0..3]`, где **`lanes[1]` левая,
`lanes[2]` правая** (крайние — соседние полосы, не используются), у каждой `y[]`, `prob`, `y_std[]`;
собственный план модели `plan_x[]`/`plan_y[]` с курсом `plan_yaw[]` и его скоростью `plan_yaw_rate[]`;
метки `capture_ts_ms`, `infer_ts_ms`, `frame_id`.

### 1.1 Основа — план модели, а не центр полосы

```cpp
out.polyline.push_back({x, y});   // из plan_x/plan_y, только x >= 1.0
```

Опора **начинается** как план supercombo; линии разметки её потом лишь подправят. Отсечка `x >= 1.0`
убирает точки под бампером, где план численно шумный. `plan_poly` сохраняется целиком — он нужен MPC.

Метка времени берётся из **`capture_ts_ms`**, то есть из момента съёмки, а не публикации. По ней на этапе 3
считается возраст опоры; со временем публикации задержка инференса стала бы невидимой.

### 1.2 Доверие к линии — два множителя

```cpp
l_prob  = softLaneProb(lanes(1).prob(), min_lane_prob /* 0.3 */);
l_prob *= stdConfidence(medianLaneStd(lanes(1), ll, lane_std_range_m), lane_std_good_m, lane_std_bad_m);
```

**Вероятность.** `softLaneProb` — не порог, а плавный переход: ниже 0.3 строго ноль, выше линейно растёт до
1 на отрезке [0.3, 1.0]. Линия с вероятностью 0.31 не получает полный вес.

**σ модели.** `medianLaneStd` берёт медиану `y_std` по окну **5…`lane_std_range_m`** (сейчас 20 м, было 40).
`stdConfidence` гасит линейно: σ ≤ `good` (0.3) → 1.0, σ ≥ `bad` (1.5) → **0.0**, между — линейно. Шумная
линия обнуляется полностью, а не становится легче.

Про выбор окна: измерено на заезде `2026_08_06_00_36_42`, худшая линия по полосам —

| участок | 5–20 м | 5–40 м | 20–40 м | 40–80 м |
|---|---|---|---|---|
| прямая | 0.11 | 0.14 | 0.20 | 0.37 |
| левая дуга | 0.58 | 0.89 | 1.49 | 4.32 |
| правая дуга | 0.34 | 0.50 | 0.78 | 1.66 |

На дуге внутренняя линия уходит из кадра, и её дальние отсчёты — экстраполяция. Сводка по 5–40 м позволяла
«я не видел так далеко» ветировать линию, ближняя половина которой в порядке. Поднимать `lane_std_bad_m`
пробовали свипом по тому же заезду и отвергли: 2.0 оставляет худшую правую дугу ровно на 0.00, 2.5 покупает
0.05 м.

**Важная оговорка:** прогноз выигрыша от сужения окна не воспроизводится и остаётся открытым вопросом
(задача #23). Скоринг одним скриптом по обоим окнам даёт σ p90 на дугах 0.70 → 0.63 и 0.76 → 0.70, а долю
кадров, где σ обнуляет линию, 15 % → 14 % и 4 % → 2 %. Медианный вес смешивания не двигается вообще, потому
что медиана σ (0.13–0.32) далеко ниже порога 1.5 — весь эффект в хвосте.

### 1.3 Ширина полосы — медленный фильтр с памятью

```cpp
state->lane_width_m += 0.01 * (w_med - state->lane_width_m);
```

Ширина — среднее `|y_правая − y_левая|` по 5–40 м, но в дело идёт фильтр с α = 0.01, то есть постоянная
времени около **7 секунд** на 14 Гц. Причина: ширина используется для восстановления центра по **одной**
линии, и если бы она скакала в момент потери линии, центр прыгал бы вместе с ней. Годный диапазон 2.6–4.6 м.

### 1.4 Центр полосы, восстановленный дважды

```cpp
from_l = yl + 0.5 * w;      // центр по левой
from_r = yr - 0.5 * w;      // центр по правой
lane_y = (l_prob * from_l + r_prob * from_r) / (l_prob + r_prob + 1e-6);
```

Центр считается **независимо от каждой линии** и взвешивается доверием. Поэтому потеря одной линии не рвёт
опору: центр живёт по второй, используя отфильтрованную ширину. Обычное `(yl + yr)/2` так не умеет.

`anchored = l_prob > 0 && r_prob > 0 && width_ok` — флаг «полоса найдена», уезжает дальше в сообщении.

### 1.5 Смешивание

```cpp
d_prob = (l_prob + r_prob - l_prob * r_prob) * lane_blend_scale;   // scale = 0.6
pt.y() = d_prob * y_lane + (1 - d_prob) * pt.y();
```

Вес `l + r − l·r` — вероятностное «или»: хватает одной уверенной линии, две дают больше. Затем масштаб
`path_lane_blend_scale = 0.6`: даже при идеальных линиях опора остаётся смесью 60 % полосы и 40 % плана
модели.

Три ветки выхода: `scale = 0` → план модели как есть; `d_prob ≈ 0` при живом плане → **тоже план модели**
(здесь теряется дуга, когда σ вышла за порог); `d_prob > 0` → интерполяция `y_lane` на сетку плана через
`interpY` и смешивание точка за точкой.

### 1.6 Два сдвига всей опоры

`shift = camera_offset_m + center`:

* **`camera_offset_m`** (0.05 м) — камера стоит не по центру машины, калибровочная поправка;
* **`center_force_m`** — подтягивание к центру полосы, **сейчас выключено** (`center_force_gain = 0`).
  Если включить: считается от смещения в точке машины (`fitAtZero`, квадратичная аппроксимация по 0–30 м),
  гасится на узкой и очень широкой полосе рампами, и ослабляется в `center_force_turn_scale = 0.7` раза,
  когда тянет **внутрь** поворота (`cf * kappa > 0`) — чтобы не срезать дугу.

### Выход этапа 1

`LanePathMsg` → `vision/path`: `polyline` (опора), `plan_poly` / `plan_yaw` / `plan_yaw_rate`,
`lane_anchored`, `lane_width_m`, `lane_offset_m`, `center_force_m`, `capture_ts_us`, `frame_id`, плюс
`p_*` — значения ручек, с которыми считалась опора.

Все шесть ручек зарегистрированы через `registerParameter`, то есть меняются на ходу; вся геометрия — в
метрах системы машины, x вперёд, **y влево-положительно**.

## Этап 2. Из полилинии в угол колёс

`services/planner.cpp`, `onLanes` → `step` → `FpPlanner` (контроллер `fp` по умолчанию).

### 2.0 Скоростной гейт с гистерезисом

```cpp
gate_on = min_control_speed_mps + hyst;                       // 1.5 + 0.5 = 2.0
if (open ? speed < 1.5 : speed < 2.0) { ...reset...; status = "low_speed"; }
```

Гистерезис обязателен: на каждом выключении **сбрасывается состояние** — MPC, фильтр темпа кривизны, PID,
EMA, память предыдущего угла. Мигание гейта в пробке означало бы контроллер, который вечно стартует с нуля.

### 2.1 Реальный темп кадров

`updateFrameDt` считает `frame_dt_s_` по меткам съёмки соседних кадров, сглаживает EMA с α = 0.3 и зажимает.
Это не диагностика: этим MPC интегрирует и из этого считается разрешённый прирост кривизны за кадр. С
номинальными 1/20 с при реальных 78 мс контур считал бы, что имеет право менять кривизну вчетверо медленнее,
чем идёт время.

### 2.2 Состояние машины относительно пути

`estimatePathLateralState` сворачивает полилинию в три числа: `cte_m` (боковое отклонение в точке машины),
`epsi_rad` (угловое расхождение курса), `kappa` (кривизна пути). Это вход MPC; `curvature` здесь ещё
геометрия, а не команда.

### 2.3 MPC получает больше, чем полилинию

```cpp
sol = fp_mpc_.update(speed, chassis_.yaw_rate, Lf, polyline_ego,
                     plan_poly, plan_yaw, plan_yaw_rate, frame_dt_s_);
```

На вход идут **и опора, и план модели, и его курс с угловой скоростью**, плюс **измеренная скорость рыска с
CAN**. То есть решается не «догнать полилинию», а «пройти траекторию с учётом того, как машина уже
вращается». Внутри MPC фрейм с **y направо** (`poly_left.emplace_back(p.x(), -p.y())`) — отсюда минус в
`steer_rad = -steerFromCurvature(...)`.

### 2.4 `lagAdjustedCurvature` — сердце этапа

`lateral/flowpilot_mpc.cpp`:

```cpp
delay      = max(steer_delay_s /* 0.35 */, dt);
kappa0     = r_sol[0] / v;                     // кривизна сейчас
psi_delay  = interpAtTime(delay, psi_sol);     // курс, набранный за время задержки
avg_kappa  = psi_delay / (v * delay);          // средняя кривизна на интервале
desired    = 2 * avg_kappa - kappa0;           // линейная экстраполяция к концу интервала
desired    = clamp(desired, kappa0 ± max_lateral_jerk / v² * dt);
```

Три идеи:

**Почему через `psi`, а не поточечно по кривизне.** MPC вправе спланировать «повернуть и вернуть» внутри
времени задержки. Такие коррекции никогда не доедут до колёс — они закончатся раньше, чем актюатор
среагирует. Курс `psi` — интеграл, он эти качели усредняет.

**Почему `2·avg − kappa0`.** Линейная экстраполяция: если средняя кривизна на интервале `avg`, а сейчас
`kappa0`, то в конце будет примерно `2·avg − kappa0`. Командуем то, что понадобится **к моменту, когда
команда доедет**, а не то, что нужно сейчас.

**Ограничение по поперечному рывку.** `max_kappa_rate = max_lateral_jerk / v²`, и зажим идёт **относительно
`kappa0` за один кадр**. Ограничение темпа уставки, таким образом, в тракте **есть** — но живёт внутри MPC и
в единицах кривизны; после превращения в угол на 14 Гц шаг уставки всё равно доходит до 3.8° (p99 на низкой
скорости).

### 2.5 Кривизна в угол — через модель машины

```cpp
steer_rad = -steerFromCurvature(kappa_cmd, speed, Lf, slipFactorOrZero());
```

`δ = atan(κ·L·(1 − slip·v²))` с `tire_stiffness_factor = 0.64`: поправка 3.6 % на 6 м/с и 62 % на 25 м/с.
Здесь же используется **выученная** жёсткость, если включён `lane_keep.use_learned_params`
(`effectiveStiffnessFactor()`).

### 2.6 Три ограничителя подряд

```cpp
lim = mpcMaxSteerRad(v) = clamp(low_speed_deg + deg_per_mps·v, low_deg, min(max_steer_deg, 25));
steer_rad = clamp(steer_rad, ±lim);                            // 1) предел угла, растёт со скоростью
steer_rad = last + clamp(Δ, ±steer_slew_limit_deg);            // 2) темп внутри MPC-пути
// в onLanes:
dkappa_max = mpc_max_lateral_jerk / v_eff² * frame_dt;
slew = min(dkappa_max * Lf, steer_slew_limit_deg);             // 3) минимум из физики и потолка
```

Первый растёт со скоростью: на парковке позволено мало, на трассе больше. Третий — самый осмысленный:
предел скорости угла есть **минимум из физического (по рывку) и жёсткого (по градусам)**; на высокой скорости
режет физика, на низкой — потолок. Срабатывание видно во флаге `dbg.slew_clipped`.

`kMaxPubGapFrames = 10`: если команды не было десять кадров, память предыдущего угла забывается, чтобы после
паузы «скорость» не считалась относительно устаревшего значения.

### 2.7 Угол колёс становится углом руля

```cpp
desired_swa_deg_ = steer_sign_ * (steer_rad_deg) * effectiveSteerRatio() + effectiveAngleOffsetDeg();
```

`steer_sign = −1`: на этой машине положительный угол на CAN — поворот **влево**, а наш фрейм считает вправо.
Проверено регрессией измеренного ISO-рыска на кинематическое предсказание: наклон +0.824 при корреляции
0.987 на 28 636 отсчётах в дугах. Тот же знак отсутствовал в порте paramsd и загнал оценщик в границы —
см. §5a бэклога.

При статусе не `ok` уставка **обнуляется** и PID сбрасывается. Сброс правильный; но сервис **не знает**,
дошла ли команда до рейки (этап 4), поэтому при закрытом гейте панды продолжает считать, будто рулит.

### Выход этапа 2

`LaneKeepOutput` → `control/lane_keep`: `steer_rad`, `curvature` (уже команда), `desired_swa_deg`, `cte_m`,
`epsi_rad`, `status` и `dbg.*`, где видна каждая ступень: `mpc_kappa_path` → `mpc_kappa_used` →
`mpc_delta_vp_rad` → `mpc_delta_clamped_rad`.

**До этого момента обратной связи по фактическому углу руля нет вообще.** Всё это — планирование в открытом
контуре.

## Этап 3. Угол руля → момент (угловой PID, 100 Гц)

`AngleControl::update` в `lateral/angle_control.h`, вызывается из `services/control.cpp`; сам регулятор — `utils/lat_control_pid.h`.

### 3.1 Темп из фактических интервалов

```cpp
dt = clamp((now() - last_pid_us_) * 1e-6, 0.005, 0.2);
lat_.setRate(1.0 / dt);
```

Интегральный канал масштабируется на `i_rate_ = 1/rate`, поэтому фиксированный темп означал бы неверный
`k_i`. `now()` — **часы middleware**, не стенные: сервис раньше читал `utils::getCurrentTimestamp()` напрямую,
и в офлайн-реплее это делало опору устаревшей на часы, гасило каждую команду и подсовывало PID бессмысленный
`dt`. Исправлено 2026-08-06.

### 3.2 Три гейта

```cpp
age_s = (now_us - capture_ts_us) * 1e-6;  if (age_s > lane_max_age_s) status = "stale";
if (blinker_on || hold) status = "blinker";
active = steer_output_enabled_ && have_desired_ && have_chassis_ && has_target && status == "ok";
```

Гейт устаревания сравнивает **время съёмки кадра** с текущим, то есть измеряет полный возраст опоры вместе с
инференсом и очередями.

Автомат поворотника **должен исполняться на каждом тике**, включая те, где статус уже `blinker`: иначе спад
флага не зафиксируется и таймер возврата начнёт отсчёт не с того момента. Условным сделано только присвоение
статуса.

### 3.3 Сам PID

```cpp
error = desired_swa_deg - actual_swa_deg;     // в ГРАДУСАХ руля
p = error * k_p;                              // k_p = 0.6
f = desired_swa_deg * v * v * k_f;            // k_f = 6e-5
out = clamp(p + i + f, -1, +1);               // выход нормирован ±1
```

Канал `d` не используется (тождественно ноль). Коэффициенты 0.6 / 0.2 / 6e-5 — те же, что у dragonpilot для
этой машины (подтверждено по её собственному `carParams` из снятых rlog).

**P выходит в упор при ошибке 1.67°** (`1 / 0.6`). Дальше выход пришпилен, и 2° ошибки неотличимы от 20° —
контур в этом режиме релейный, а не пропорциональный. Измерено с двух сторон:

* по нашему багу `2026_08_06_18_27_12` с включённым ассистом: ошибка выше 1.67° в 7.3 % кадров, и в 99 % из
  них запрос стоит в упоре 300; полный разворот запроса за 0.5 с — на 7.2 % кадров дуг против 1.3 % прямых;
* дифференциальным прогоном логов comma через наш стек на одних входах: наш момент в упоре в 72.6 % кадров
  против их 46.9 %, и в 52–60 % кадров мы в упоре даже там, где их момент меньше 150 cNm.

**I:** `i += error * k_i * dt` с антивиндапом
```cpp
if ((error >= 0 && (control_try <= pos_limit || i_new < 0)) || (error <= 0 && ...)) i_ = i_new;
```
Интегрировать разрешено, только если это не загоняет глубже в упор либо интеграл идёт назад. Логика верная,
но смотрит **только на предел ±1** и ничего не знает о темповом ограничителе на CAN: при развороте момента
применённое значение ползёт со скоростью 200 cNm/с, выход PID формально не в упоре, и интеграл набирается на
ошибку, которую физически нельзя убрать. Апстрим передаёт `freeze_integrator = steer_limited`; у нас
параметр в сигнатуре есть, но не передаётся.

**F:** упреждение по самоустанавливающему моменту. В коде форма `desired_swa · (v² + v0²) · k_f`, где `v0`
(`lat_pid_ff_floor_mps`) добавлен 2026-08-09 ровно затем, чтобы член не исчезал на малой скорости. **В боевом
конфиге `v0 = 0`**, дефолт в коде — 9.8 м/с, то есть едет старая форма `desired_swa · v² · 6e-5`. Измерено по
`pid_f` на беге 2026-08-21: **1.3 cNm ниже 8 м/с, 3.2 на 8–15, 4.3 на 15–24 — из 300**, а подразумеваемый
`k_f` 5.63e-05 против конфигурационного 6e-05 подтверждает, что порог был нулевой. Трение рейки (по
выученному comma `frictionCoefficientRaw = 0.192`, то есть ≈ 57 cNm) не компенсируется ничем.

**`override`** — водитель на руле: `i_ -= i_unwind_rate_ * sign(i_)` с `i_unwind_rate = 0.3/rate`, то есть
интеграл **разматывается** примерно за 3 секунды, а не просто замирает. Иначе после отпускания руля
накопленный интеграл дал бы рывок.

### 3.4 Нормированный выход в cNm

```cpp
torque  = lround(out.steer_norm * max_torque_cnm_ /* 300 */);
enabled = steer_output_enabled_ && has_target && status == "ok" && have_desired_;
cmd.set_torque_cnm(enabled ? torque : 0);
```

**Ловушка, стоящая внимания:** `steer_norm` означает **разное на двух путях**. На пути зрения (этап 2) это
`steer_rad / max_steer_rad`, геометрическая нормировка угла; на пути шасси то же поле перезаписывается
выходом PID. `publishSteer` вызывается только со второго пути, так что на CAN уходит момент, а
`control/lane_keep`, опубликованный с первого, несёт под тем же именем другую величину. На этом уже один раз
сломался дифференциальный стенд.

Вместе с моментом уезжают `capture_ts_ms`, `vision_ts_ms`, `chassis_ts_ms`, `publish_ts_ms` — вся цепочка
задержек от съёмки до команды в одном сообщении.

### Выход этапа 3

`SteerCommand` → `controls/steer` (знаковый момент cNm + `enabled`), и `control/lane_keep_debug` с
`desired_swa_deg` / `actual_swa_deg` / `angle_error_deg` / `torque_cnm` — теми полями, по которым считается
качество слежения.

**`enabled` здесь — наше разрешение, а не факт актюации.**

## Этап 4. Момент → кадр на шине

`services/platform.cpp` → `platform/volkswagen/carcontroller.cpp` → `platform/volkswagen/mqbcan.cpp`.

### 4.1 Приём команды

```cpp
torque = clamp(cmd.torque_cnm(), ±300);
hca_cmd_enabled_ = cmd.enabled() && (torque != 0);      // ноль момента = «не рулим»
hca_cmd_ts_ms_ = utils::getCurrentTimestamp();
```

`torque != 0` означает, что **нулевой момент трактуется как выключение**, а не как «рули с нулевым усилием».
Отсюда потом сброс `hca_enabled` на каждом переходе через нуль.

Здесь **стенные часы** — тот же дефект, что был на этапе 3 и пока не исправлен: в реплее через middleware это
сломает свежесть команды.

### 4.2 Три таймера

```cpp
scheduleTimer(10,  pandaRxCallback,       "rx");      // 100 Гц, чтение шины
scheduleTimer(10,  carControllerCallback, "tx");      // 100 Гц, передача
scheduleTimer(100, pandaStateCallback,    "state");   // 10 Гц, health
```

Передача **не привязана к приходу команды**: таймер всегда отправляет то, что лежит в `hca_cmd_steer_`.
Отсюда нужен гейт свежести `cmd_fresh = (now - hca_cmd_ts_ms_) <= 250 мс`.

### 4.3 `latActive` — одно условие чужое

```cpp
cc.latActive = cmd_fresh && hca_cmd_enabled_ && safety_.lastControlsAllowed();
```

`controls_allowed` ставит **панда**, и для MQB так (`safety_volkswagen_mqb.h`):

```c
cruise_engaged = (TSK_06.TSK_Status == 3 || 4 || 5);   // штатный круиз ЗАДЕЙСТВОВАН
acc_main_on    = cruise_engaged || TSK_Status == 2;    // 2 = главный включён, не задействован
if (!volkswagen_longitudinal) pcm_cruise_check(cruise_engaged);
if (!acc_main_on) controls_allowed = false;
```

Рулить разрешено **только пока штатный круиз реально задействован**. Штатный круиз VW отваливается ниже
~30 км/ч и при торможении — то есть ровно на медленной крутой дуге и её выходе. Измерено на
`2026_08_06_18_27_12`: `TSK_Status == 2` — 70.7 % времени, `controls_allowed` истинно 29.3 %; там, где
контроллер хотел рулить, ассист реально был включён в 2.6 % кадров при 5–8 м/с и 18.3 % при 8–12 м/с. Где
ошибка угла превышала 5°, ассист был включён в 12.9 % кадров. Подробности и что не портировано (ATL/ALKA
dragonpilot) — §4a бэклога, задача #24.

### 4.4 Передача раз в два тика

`if (frame_ % STEER_STEP == 0)` при `STEER_STEP = 2` даёт HCA_01 на **50 Гц**. Отсюда все темповые числа:
`STEER_DELTA_UP = 4` cNm за кадр 20 мс = **200 cNm/с**, `DELTA_DOWN = 10` = 500 cNm/с. Подъём 0 → 300 занимает
1.5 с, разворот +300 → −300 около 2.1 с.

### 4.5 Локальные гейты `CarController`

```cpp
eps_ok     = epsHcaAllowsSteer(epsHcaStatus);        // только Ready(3) или Active(5)
standstill = CS.standstill || |vEgo| < 0.3;
lat_active = CC.latActive && eps_ok && !standstill;
```

`eps_ok` — наша добавка (у апстрима проверка живёт в carstate через `steerFault*`). На разобранном заезде EPS
был `Ready` 71.6 % / `Active` 28.4 % и **ни разу** `Fault` или `Rejected`, так что этот гейт ничего не отнял.

### 4.6 Ограничитель момента — два независимых зажима

```cpp
driver_max = STEER_MAX + (ALLOWANCE + driver_torque * FACTOR) * MULTIPLIER;   // 300 + (80 + T·1)·3
apply = clamp(apply, min_allowed, max_allowed);                              // 1) допуск по водителю
if (last > 0) apply = clamp(apply, max(last - 10, -4), last + 4);
else          apply = clamp(apply, last - 4, min(last + 10, 4));             // 2) темп
```

**Допуск по водителю** не «уменьшает ассист, когда водитель крутит», а **сужает разрешённый диапазон со
стороны, противоположной водителю**: если водитель тянет влево с моментом 100, то вправо разрешат до
`−300 + (−80 + 100)·3 = −240`, а влево — как обычно. Система не мешает водителю и не бросает руль.

**Темп асимметричен:** наращивать магнитуду по 4 cNm за кадр, сбрасывать по 10. По комментарию панды рейка
держит 5 Нм/с, а панда навязывает 2 Нм/с на рост. Отпустить руль всегда можно быстрее, чем схватить.

Тонкость в ветках: при `last > 0` нижняя граница `max(last − 10, −4)`, то есть через нуль сразу в −4, не
дальше. **Каждый разворот момента обязательно проходит через ноль.**

### 4.7 Три костыля против отказа EPS

```cpp
if (apply_steer == 0) { hca_enabled = false; frame_count = 0; }               // 1) ноль = выкл
if (frame_count >= 118 * 50) { hca_enabled = false; frame_count = 0; }        // 2) таймаут 118 с
if (last == apply && ++same > 1.9 * 50) { apply -= sign(apply); same = 0; }   // 3) дрожь на 1 cNm
```

Все три перенесены из апстрима и обходят состояние EPS «отказано» (`HCA_Status = 4`): VW не позволяет держать
один момент дольше ~6 с, рулить непрерывно дольше 360 с и слать больше 3 Нм.

Побочный эффект первого: переход через нуль **выключает ассист**. Измерено — 2.9 раза в минуту при включённом
ассисте.

### 4.8 Кадр `HCA_01` (0x126)

```cpp
set_bits(data, cnt,               8, 4);    // COUNTER 0..15
set_bits(data, 0x3,              12, 4);    // SET_ME_0X3
set_bits(data, |apply_steer|,    16, 14);   // Assist_Torque — магнитуда
set_bits(data, lkas_enabled,     30, 1);    // Assist_Requested
set_bits(data, apply_steer < 0,  31, 1);    // Assist_VZ — знак отдельным битом
set_bits(data, 1,                32, 1);    // HCA_Available
set_bits(data, !lkas_enabled,    33, 1);    // HCA_Standby
set_bits(data, lkas_enabled,     34, 1);    // HCA_Active
set_bits(data, 0xFE, 40, 8);  set_bits(data, 0x07, 48, 8);
data[0] = volkswagen_mqb_checksum_hca(data, 8);
```

Проверено бит в бит против `opendbc/vw_mqb_2010.dbc` и против `mqbcan.py` dragonpilot — совпадает полностью.
Момент передаётся **магнитудой плюс знаковым битом**, а не знаковым целым. Счётчик и контрольная сумма
обязательны: кадр с неверной суммой EPS отбросит молча.

### 4.9 Панда проверяет то же самое сама

```cpp
panda.set_safety_model(kVolkswagen /* 15 */, param);
panda.set_alternative_experience(kAltExpDisableDisengageOnGas /* 1 */, 0);
```

Панда независимо повторяет `steer_torque_cmd_checks` с теми же лимитами (`max_steer = 300`,
`max_rate_up = 4`, `max_rate_down = 10`) и **не пропустит** ненулевой момент при `controls_allowed = false`.
Отказы видны в `panda/health.tx_blocked`.

`alternative_experience = 1` — только `DISABLE_DISENGAGE_ON_GAS`. Флага ALKA (16 в панде dragonpilot) мы не
выставляем, поэтому always-on lateral не работает даже с их прошивкой. **Осторожно:** бит 16 в исходниках
панды flowpilot означает `ALLOW_AEB` — один бит, два смысла, зависит от прошивки.

## Где команда молча умирает

Три места, все измерены на `2026_08_06_18_27_12`:

1. **`controls_allowed` по штатному круизу** — 49 % кадров, где контроллер считал, что рулит, момента на шине
   не было вовсе (§4a, задача #24);
2. **темповый ограничитель на разворотах** — около 0.4 с из 1.4 с уходит на пересечение мёртвой полосы трения
   ±57 cNm, где руль не двигается (задача #25);
3. **`apply_steer == 0 → hca_enabled = false`** — 2.9 самовыключения в минуту.

И одно место, где тракт **врёт наверх**: ни этап 3, ни этап 2 не узнают, что этап 4 отбросил команду.
Обратной связи от актюации к контроллеру нет, поэтому PID продолжает интегрировать, отладка сообщает «рулю», и
любой анализ по `steer_output_enabled` смешивает кадры с моментом и без. Из-за этого все поперечные метрики
слежения в бэклоге до 2026-08-06 занижены — гейтить надо по `HCA_01.HCA_Active` с шины.

**Когда ассист действительно включён, слежение не хуже апстримного** — доля достигнутого угла 0.92–0.98
против 0.90–0.98 у dragonpilot на той же машине с тем же PID.

### Как смотреть видео вида сверху

```bash
cd scripts
# 1) найти участки, где рулить было разрешено, отсортированные по кривизне команды
python3 bag/bag_topdown_video.py <bag> --list-assist
# 2) снять окно оттуда
python3 bag/bag_topdown_video.py <bag> --start 2860 --duration 14 --out /tmp/hw.mp4
```

Один кадр видео = один кадр камеры. Цвет кузова машины — **факт актюации** (`HCA_01.HCA_Active` с шины), а не
наше разрешение: серая машина значит, что момент на шину не шёл, и качество слежения в этот момент оценивать
нельзя. Опора контроллера пересчитывается зеркалом `core/path_fusion.py` с параметрами, записанными в баге,
потому что сам `vision/path` в баг не пишется.
