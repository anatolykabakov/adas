# Локализация: собираем оценщик по одному датчику

Эта глава написана как сборка, а не как описание. Начинаем с самой грубой оценки того, где находится машина,
выясняем, чего она не может, добавляем один датчик — и повторяем. Каждый шаг умещается в несколько строк,
которые можно запустить, и каждому соответствует переключатель в `config.json`: датчик можно отключить на
настоящей машине и увидеть тот самый отказ, что предсказан в тексте.

| шаг | что добавляем | что исправляет | чего не может |
|---|---|---|---|
| 1 | скорость колёс и угол руля (велосипедная модель) | поза из ничего | уплывает без ограничения; работает только при верной модели |
| 2 | гироскоп телефона как измерение скорости рыска | курс идёт за датчиком, а не за моделью | позиция всё равно уплывает; помогает только при правильном слиянии |
| 3 | позиция и курс GPS | ограниченные позиция и курс | **прячет** ошибки шагов 1–2; в тоннеле бесполезен |
| 4 | скорость как состояние, скорость GPS | коррекция, доживающая до следующего тика | масштабную ошибку всё равно не выучить |
| 5 | крен дороги из поперечного акселерометра | отделить поперечный уклон от недокрута машины | 0.65° после десяти секунд усреднения, и не лучше; уклона по-прежнему нет |

```{admonition} Читайте эту главу про оценщик, а не про руление
:class: note
В тракте управления никто не подписан на `localization/pose`. Единственный подписчик — отладочный вывод, а
поперечный контроллер берёт скорость рыска прямо из `vehicle/chassis`. Поэтому здесь удобнее всего в проекте
изучать оценщик: ошибись хоть грубо — машина этого не заметит. Обратная сторона в том, что каждое утверждение
ниже приходилось проверять по GNSS, а не по принципу «машина поехала — значит, порядок».
```

Опорные точки в коде, в том порядке, в каком глава до них добирается:

* `SpeedFilter` (`utils/speed_filter.h`) — скорости колёс → скорость и ускорение
* `ImuCalibrator` / `ImuCalibService` — IMU телефона → скорость рыска машины
* `GpsLocalProjector` — широта и долгота → метры на восток и север
* `VehicleEKF` / `OnlineLocalizer` / `LocalizationService` — слияние → `localization/pose`

RPY камеры для warp Supercombo — **отдельная** история ([калибровка](../Calibration/Overview.md)):
с IMU у неё общий только prior крепления, и она может опционально подавать в EKF скорость рыска от камерной одометрии.

## Переключатели, которыми вы будете пользоваться


Каждый источник вынесен в отдельный ключ: слитая оценка не сообщает, каким датчиком она держится, а когда
несколько источников согласны между собой, сломанный прячется за остальными.

```json
"localization": {
  "use_gps_position": true,
  "use_gps_course": true,
  "use_gps_velocity": true,
  "use_imu_yaw_rate": true,
  "use_chassis_yaw_rate": true,
  "use_camera_odometry": true,
  "use_bicycle_model": true
}
```

Это не боевая функция — в машине все они должны быть включены. Это инструмент для остальной главы, и именно
так был наконец измерен дефект из шага 2: с включённым курсом GPS ошибка курса невидима, без него — 38° за
пять секунд.

## Шаг 0: системы координат, прежде чем что-либо ещё


Половина ошибок в этой области — не ошибки оценивания, а путаница в системах координат. Сначала наведите
порядок в терминах.

| система | оси | для чего |
|---|---|---|
| **Локальная ENU** | $x$ восток, $y$ север; начало — первый фикс GPS | `localization/pose`, отсчёты GPS после конвертации |
| **Пеленг GPS** | градусы **по часовой от севера** (Android) | курс → рыск в ENU |
| **Велосипедная / машина** | плоский рыск в ENU; $\delta$ на передней оси | предсказание EKF |
| **Машина по ISO** | $y$ **влево** | prior крепления камеры |
| **Device / Supercombo** | $y$ **вправо** | разметка, камерная одометрия (см. [системы координат](../Vision/Coordinates.md)) |

```{admonition} Одно имя топика, две начинки
:class: warning
Java публикует `sensors/gps/location` как **прото с широтой и долготой**. После `proto_convert` **под тем же
именем топика** идёт типизированный `GpsSample` в метрах ENU. Офлайн-инструменты обязаны знать, с какой
стороны конвертации они читают. Это уже не раз оборачивалось потерянным на отладку временем.
```

## Шаг 1: самая дешёвая оценка — скорость колёс и угол руля


Скорость кажется скучным входом. Это не так, и по двум причинам: она масштабирует весь поперечный тракт
(недокрут входит как $v^2$), а очевидный способ вычислить по ней ускорение неверен.

### Откуда она берётся

`ESP_02` несёт четыре скорости колёс, декодер их усредняет. Дальше upstream прогоняет это среднее через фильтр
Калмана из двух состояний (скорость, ускорение) — `CarInterfaceBase.update_speed_kf` в flowpilot — и берёт из
фильтра **и** `vEgo`, **и** `aEgo`. Мы делаем то же самое с одним отличием: их коэффициенты зашиты под такт
100 Гц, а наши вычисляются по фактическому интервалу между кадрами, потому что `ESP_02` приходит не по метроному.

### Почему нельзя просто продифференцировать

Потому что сигнал скорости колеса квантован с шагом 0.0075 км/ч, а интервал между отсчётами — около 10 мс.
Дифференцирование квантованного сигнала на коротком интервале усиливает квант в $1/dt$ раз. На настоящем
28-минутном заезде наивная конечная разность дала:

```{figure} figures/a_ego.png
---
width: 80%
---
Дифференцирование шумной скорости колёс взрывает ускорение; фильтр из двух состояний его восстанавливает
(схема измеренного RMS 4.16 → 0.062 м/с²).
```


| | конечная разность | фильтр из двух состояний |
|---|---|---|
| `a_ego` p5 / p95 | −3.85 / +3.80 м/с² | −0.57 / +0.68 |
| крайние значения | −61.5 / +74.5 м/с² | −4.0 / +3.1 |
| ск. кв. скачок между отсчётами | 4.16 м/с² | **0.062** |

Машина не может изменить ускорение на 4 м/с² за 10 мс. Это поле было шумом квантования, выступавшим под именем
ускорения. Его никто не читал — только поэтому и обошлось без вреда, — но урок в другом: неиспользуемый сигнал
не безобиден, это ловушка для того, кто воспользуется им следующим.

Отфильтрованная скорость отклоняется от сырого среднего на 0.010 м/с по медиане — то есть ничего не искажено:
ушёл лишь тот шум, который и дифференцировали.

```python
import math
import numpy as np

QUANTUM = 0.0075 / 3.6      # ESP_VL_Radgeschw_02 resolution, m/s

class SpeedFilter:
    """Two-state (speed, accel) Kalman over the wheel-speed average. Mirror of speed_filter.h."""

    def __init__(self, accel_process_noise=1.5, speed_noise=0.05, jump=2.0, factor=1.0):
        self.qa, self.r, self.jump, self.factor = accel_process_noise, speed_noise**2, jump, factor
        self.inited = False

    def update(self, v_raw, dt):
        z = v_raw * self.factor
        if not self.inited or not dt > 0 or dt > 0.5 or abs(z - self.v) > self.jump:
            self.v, self.a = z, 0.0
            self.pvv, self.pva, self.paa = self.r, 0.0, 1.0
            self.inited = True
            return
        self.v += self.a * dt                                   # predict
        q = self.qa**2 * dt
        pvv = self.pvv + 2 * dt * self.pva + dt**2 * self.paa + q * dt**2 / 3
        pva = self.pva + dt * self.paa + q * dt / 2
        self.pvv, self.pva, self.paa = pvv, pva, self.paa + q
        s = self.pvv + self.r                                   # update on speed only
        kv, ka = self.pvv / s, self.pva / s
        innov = z - self.v
        self.v += kv * innov
        self.a += ka * innov
        self.pvv, self.pva, self.paa = (1 - kv) * self.pvv, (1 - kv) * self.pva, self.paa - ka * self.pva


def quantise(v):
    return round(v / QUANTUM) * QUANTUM

# Steady 20 m/s with a little road noise: what does each method call "acceleration"?
rng = np.random.default_rng(0)
f = SpeedFilter()
naive, filtered, prev = [], [], None
for _ in range(3000):
    z = quantise(20.0 + rng.normal(0, 0.02))
    if prev is not None:
        naive.append((z - prev) / 0.01)
    prev = z
    f.update(z, 0.01)
    filtered.append(f.a)

print(f"naive    : |a| up to {max(abs(x) for x in naive):7.1f} m/s^2")
print(f"filtered : |a| up to {max(abs(x) for x in filtered[500:]):7.2f} m/s^2")
```

### Радиус колеса, который никто не откалибровал

Скорость колеса — это длина окружности, умноженная на частоту вращения, поэтому изношенная или недокачанная
шина смещает весь сигнал на постоянную величину. Сверено с доплеровской скоростью GNSS — на трёхмерном фиксе
она точна до сантиметров в секунду, куда лучше любой шины — на двух заездах:

| | бег 08-06 | бег 08-04 |
|---|---|---|
| CAN колёса / доплер GNSS | **1.0117** | **1.0120** |
| остаток после снятия масштаба | 0.101 м/с | 0.066 м/с |
| масштаб при 5–10 / 10–15 / 15–20 / 20–25 м/с | 1.022 / 1.011 / 1.011 / 1.013 | 1.013 / 1.013 / 1.015 / 1.011 |

CAN завышает на **1.2 %**, и масштаб не зависит от диапазона скорости. В этом постоянстве и весь аргумент:
пробуксовка росла бы с нагрузкой и скоростью, отказывающий датчик не был бы настолько стабилен, а радиус
колеса — величина постоянная. Для этого и существует `SpeedFilter::Config::wheel_speed_factor`, по умолчанию
1.0, чтобы поправку вносили осознанно.

```{admonition} Ошибка скорости в 1.2 % — не задача на 1.2 %
:class: warning
Компенсация недокрута — это $\kappa = \delta / (L(1 + K v^2))$, скорость входит в квадрате. А метрический
масштаб модели, который в этом проекте фигурирует как 0.888, измерялся *по скорости колёс*; относительно
истины он равен 0.899. Когда сам эталон смещён, это смещение наследует каждое производное число.
```
